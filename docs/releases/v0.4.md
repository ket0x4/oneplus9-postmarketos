## What's new since v0.3

This release is about the kernel build: the config now describes this hardware instead of a generic
arm64 machine, and the toolchain is the combination that was verified to boot on a phone. Nothing
changes for the hardware drivers the phones use.

### The config carries this phone, not every arm64 machine

`kernel/op9.config` is down from 10,018 to 9,505 lines with only the sm8350 platform selected
(`ARCH_QCOM`). Drivers for other SoCs, GPUs, Bluetooth and Ethernet vendors, RAID/SAS HBAs, ATA, MTD,
CAN, DVB and audio platforms for other SoCs are off, so neither the build nor the module tree carries
what the phone never probes. Everything the device trees ask for stays: the Adreno/MSM display stack,
WCN6855 Wi-Fi and Bluetooth (`ath11k`, `btqca`), UFS, USB/Type-C with the FSA4480 mux,
fastrpc/QRTR for the DSPs, the WCD9380/TFA9874 audio path, the IMX/OV camera sensors and the AW8697
haptics.

Wireless and filesystems are kept in full, because both are plausible add-ons in desktop mode. The
common USB Wi-Fi adapters are modules (`mt7601u`, `mt76x0u`/`mt76x2u`, `mt7921u`/`mt7925u`,
`rtl8xxxu`, `rtw88`/`rtw89`, `ath9k_htc`, `rt2800usb`, `brcmfmac`, `mwifiex`, `rsi` and others), and
so are `btrfs`, `exFAT`, `NTFS3` and `9p`, so a USB dongle or an external disk works.

Sizes, measured on the same 167-patch series:

| | v0.3 | v0.4 |
|---|---|---|
| `Image` | 37.9 MB | 34.0 MB |
| modules installed | 77 MB, 1253 `.ko` | 21 MB, 1210 `.ko.zst` |

Modules are zstd-compressed and the kernel decompresses them itself (`CONFIG_MODULE_DECOMPRESS`), so
nothing on the rootfs needs to change.

### The build is faster without changing the artifact

- `kernel/build.sh` wraps the compiler in `ccache` when it is installed. A patch-series change that
  used to cost a full recompile now reuses what did not change; the output is unaffected.
- The config is copied only when it differs, and the built-in device trees are copied only when they
  change, so a rerun that changed nothing does no work: 21 s and zero compiles here, where it used to
  relink the kernel every time.
- CI keeps the ccache between runs and pins the compiler version in the build manifest.

### GCC, no LTO

The kernel is built with `aarch64-linux-gnu-gcc` and `CONFIG_LTO_NONE`. A clang ThinLTO build
(`TOOLCHAIN=clang`) compiles cleanly with LLVM 23 but **does not boot** on this phone: it hangs at the
logo and leaves no pstore record, so it dies before the ramoops console exists. It is kept in the
script for testing, not as the default.

`CONFIG_KALLSYMS_ALL` is off. The release still ships `System.map`, so symbolising a crash is done
from that or from `vmlinux`, not from `/proc/kallsyms`.

### Test a kernel on the spare slot first

`postmarketos/GUIDE.md` now documents the procedure that this work needed, after a boot image was
written to `boot_a` and the phone looped at the logo:

```sh
fastboot flash boot_b <candidate.img>
fastboot set_active b
fastboot reboot
# back to the known-good image if it does not come up:
fastboot set_active a
```

Two rules make that test meaningful, and both are in the guide:

- **The modules must match the kernel.** `CONFIG_MODVERSIONS` is off, so a module built from a
  different config loads without complaint and then corrupts the running kernel — which is what
  produced the `unable to handle kernel paging request` panics seen while testing. Build the candidate
  with `KERNEL_LOCALVERSION=-test` and install it into its own `/lib/modules/<release>` directory, so
  a boot loop says something about the kernel rather than about mismatched modules.
- **A boot loop at the logo does not prove the config wrong.** Separating the two showed the pruned
  config boots fine on GCC; only the LTO build fails.

### Upgrading from v0.3

Install the new `Image`, modules and `initramfs.gz` as usual: the boot image is packed from your own
`vendor_boot.img` with `scripts/op9-boot-image.sh`, unchanged. Replace the installed module tree with
the one from this release; the release name is still `7.3.0-op9+`, so the old `.ko` files must be
removed rather than merged with the new `.ko.zst` ones:

```sh
sudo rm -rf /lib/modules/7.3.0-op9+
sudo tar -C /lib/modules -xf modules-7.3.0-op9+.tar.zst
sudo depmod -a
```

Wireless adapters or filesystems you relied on before are still there; the pruning only removed
drivers for hardware this phone does not have.
